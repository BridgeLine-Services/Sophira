# SOPHIRA — TESTING TONIGHT (private test channel)

Exact steps to test Sophira tonight without any app-store listing. Every
path below works from the live PWA at **https://sophira.vercel.app**
(no store review, no install gate). Native artifacts, when published by
the release pipeline, appear on **/downloads** — the page only shows a
download button for an artifact that actually exists, with its SHA-256.

> Status of each path is stated honestly on /downloads:
> - **PWA** — fully available now (this is the primary test path).
> - **Android APK** — the release pipeline builds it; if the Android
>   signing secrets are not configured it is labeled **UNSIGNED APK**
>   with its installation requirements (adb or self-signing).
> - **Desktop installers** — produced by the release pipeline for the
>   platforms the pipeline supports; the page shows only real artifacts.
> - **iOS** — never a fake "unsigned IPA": use the PWA now, or the
>   development/ad-hoc/TestFlight path once Apple signing is configured.
> - Everything is marked **TEST BUILD** — artifacts may not be
>   production-signed.

## 0. What you need

- The live URL (above) or a local checkout (`npm ci && npm run build && npm run start`).
- An email address for the OWNER account and a second one for a TEST USER.
- (Optional, for full AI features) `OPENAI_API_KEY`, search provider keys,
  and the Supabase env vars — the app runs without them and says so
  honestly; it never fakes an answer.

## 1. Install (PWA)

1. Open https://sophira.vercel.app on the phone/desktop browser.
2. iPhone Safari: Share → **Add to Home Screen**. Android Chrome: menu →
   **Install app**. Desktop Chrome/Edge: the install icon in the address bar.
3. Launch from the home screen — it runs full-screen, offline-capable.

## 2. Create the owner

1. You need an invitation — the signup gate is closed by design (a DB
   trigger refuses account creation without a valid invitation).
2. First owner bootstrap: use the owner bootstrap invitation path in the
   docs (or run the SQL bootstrap from `docs/`), then sign up with the
   invite link.
3. Confirm: signing up WITHOUT an invitation fails. That is correct
   behavior, not a bug.

## 3. Configure the owner

1. Log in as the owner. Set display name in Settings.
2. Owner-only screens (members, invitations, analytics) must be reachable;
   for a non-owner they must not appear.

## 4. Create an invitation

1. Owner → Network/Members → **Invite**. Enter the test user's email.
2. Copy the generated invite link (192-bit token, single-use, expiring).

## 5. Approve the test user

1. Open the invite link in a NEW private window, sign up as the test user.
2. Try opening the SAME invite link again — it must be refused
   (single-use, atomic claim).
3. (If your flow uses join-requests: request → owner approves → a real
   invitation is issued; approval without the owner must be impossible.)

## 6. Calibrate typing

1. As the test user: Settings → Typing calibration (or the pacing setup
   in the essay screen).
2. Type the calibration passage naturally. Confirm the WPM persists and
   that the essay Output modes now show your measured pace (Instant /
   Calibrated / Slow / Custom).

## 7. Download the local model

1. Settings → Offline/local model → download (a real, pinned,
   integrity-checked local model; the progress is real).
2. Confirm the model status shows the honest state (downloaded or not).

## 8. Test offline

1. Enter offline mode from the app (or turn on airplane mode after the
   model is downloaded).
2. Ask a math/writing question in the offline panel.
3. Expect: a real response generated by the LOCAL model, with the
   offline provenance badge. No fake "success" with an invented answer.

## 9. Test math

1. Upload or type a math question in the math panel.
2. Try an image upload (OCR transcription) and a pasted equation.
3. Expect: the pipeline runs deterministically where it can, the answer
   shows its verification status, and hallucinated-looking steps are
   flagged for review, never silently presented as verified.

## 10. Test research

1. Research panel: enter a topic, start the research run.
2. Approve only the VERIFIED candidate sources (dead URLs are rejected;
   a search snippet is never treated as retrieved content).
3. "Why this source?" must show authority, relevance, date, type, and
   the assignment requirement satisfied.
4. Ask a research-grounded question and click a citation — it must open
   the exact source location (page number for PDFs, URL + retrieved
   timestamp for web).

## 11. Test essay

1. Essay panel: create an essay for an assignment (add teacher + rubric
   docs first for a full test).
2. Confirm the staged flow: plan (analysis, rubric, requirements,
   research evidence) → outline approval gate → one section at a time →
   citation/rubric/style audits → final verification.
3. If you selected a Calibrated pace, the reveal must follow your WPM.

## 12. Test rubric

1. Rubric audit on the drafted essay.
2. Expect: criteria extracted from the teacher's actual document, honest
   NEEDS REVIEW on missing evidence, and the audit persisted.

## 13. Test revocation

1. Owner → Members → **Revoke** the test user.
2. As the test user, refresh: access must be blocked IMMEDIATELY (the
   per-request status check), even with a still-valid token.
3. Owner: confirm **Restore** works (member returns with status `active`).

## 14. Test reinstatement

1. After restore, the test user logs in normally and reaches the app.
2. Revoke → restore → verify again. The restore action must actually
   succeed (this was silently broken before the 2026-10-06 fix; if
   restore fails, that is a regression — report it).

## Cross-cutting checks while testing

- Privacy: log in as the test user in one browser and the owner in
  another; confirm neither can see the other's academic content.
- Honesty: with no AI key configured, the app must say so and never
  fabricate an answer.
- Network-off fallback: with the local model downloaded and connectivity
  OFF, an ask must get a real local-model response — not a fake success.

## Forgot Password Acceptance Test

Real-user steps (perform with a real email inbox; do not skip):

A. Create a valid invited test account.
B. Confirm the account can sign in.
C. Sign out.
D. On /login, select "Forgot your password?".
E. Request a reset using the account email.
F. Open the real reset email.
G. Follow the recovery link (it returns to /reset-password in set mode).
H. Set a new password (try a mismatch first — expect a clear error; try 7
   characters — expect the minimum-length error).
I. Confirm the password was changed (the app signs you out).
J. Return to /login.
K. Confirm the OLD password now fails.
L. Confirm the NEW password succeeds.
M. Sign out.
N. Repeat D–E with a NONEXISTENT email and confirm the page shows the SAME
   generic message — it must not reveal whether the account exists.
O. Request a reset, then request another and open the FIRST link after the
   second (or wait for expiry) — confirm the page fails safely with the
   invalid/expired message and offers a fresh link. Recovery does not
   grant access: while the recovery session is open, /dashboard still
   applies the same invitation/active-access checks.
P. Confirm the reset did NOT change the user's invitation status, role,
   profile, teacher data, academic data, or permissions (compare before/after).

Note: password recovery is an ONLINE authentication operation — with
connectivity off, the page says so honestly and never pretends an email
was sent. There is no offline password reset, by design.

## Build artifacts (for maintainers)

```bash
npm ci
npm test
npm run build
npx tsc --noEmit -p tsconfig.json
npm run android:build   # needs JDK + Android SDK
npm run desktop:build   # needs Rust + Tauri system deps
```

The release pipeline (.github/workflows/release.yml) performs these on
runners with the full toolchains, attaches real artifacts, and writes
SHA-256 checksum files. Unsigned APKs are named and labeled honestly;
an unsigned iOS archive is never called an .ipa.
